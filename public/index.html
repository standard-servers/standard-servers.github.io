Standard Servers

Write server utilities and middleware once. Run them on any Fetch-based framework.

standard-context standard-middleware

The problem

Modern JavaScript server frameworks have all settled on the Fetch API: a Request comes in and a Response goes out. But each one wraps the request in its own context or event object, so a utility or middleware written for one framework doesn't work in the others. 

// H3
app.use((event) => console.log(event.req.method, event.url.pathname));

// Hono
app.use(async (c, next) => {
  console.log(c.req.method, c.req.path);
  await next();
});

// SvelteKit
export const handle = ({ event, resolve }) => {
  console.log(event.request.method, event.url.pathname);
  return resolve(event);
};

The same logger, written three times. Multiply that by every library and every framework.

The idea

Inspired by Standard Schema, frameworks keep their own context and add one extra property to it: ~standard. Library authors read the request and shape the response through it, without knowing which framework they run in. Frameworks can adopt it without breaking changes.

Proposal 1

StandardContext

A standard way to read the incoming Request and prepare the outgoing Response. Frameworks can also expose runtime-specific data and waitUntil. 

export type StandardContext<C = {}, R = unknown, W = unknown> = C & {
  readonly "~standard": StandardContext.Props<R, W>;
};

export declare namespace StandardContext {
  export interface Props<R = unknown, W = unknown> {
    /** Name of the server framework */
    readonly vendor: string;
    /** Incoming web Request */
    readonly req: Request;
    /** Prepared response modifiers */
    readonly res: PreparedResponse;
    /** Runtime specific data, e.g. { node: { req, res } } */
    readonly runtime?: R;
    /** Wait until a promise has resolved */
    readonly waitUntil?: (promise: Promise<any>) => W;
  }

  export interface PreparedResponse {
    body?: BodyInit | null;
    status?: number;
    headers?: Headers;
  }
}
Proposal 2

StandardMiddleware

Built on top of StandardContext: a middleware is an async function of (context, next). Frameworks compose a stack of them like koa-compose. Code before await next() runs on the way in, code after runs on the way out. 

export type StandardNext<Args extends unknown[] = [], T = unknown> = (
  ...args: Args
) => Promise<T>;

export type StandardMiddleware<
  C extends StandardContext = StandardContext,
  N extends StandardNext = StandardNext,
  R = void,
> = (context: C, next: N) => Promise<R>;

How it fits together

Library author

Write middleware once

import type { StandardMiddleware } from "standard-middleware";

export const logger: StandardMiddleware = async (c, next) => {
  await next();

  const { req, res } = c["~standard"];
  console.log(res.status ?? 200, req.method, req.url);
};

export const addVendorHeader: StandardMiddleware = async (c, next) => {
  c["~standard"].res.headers?.set("x-vendor", c["~standard"].vendor);
  await next();
};
Framework author

Expose ~standard on the context

In H3 the context already matches the shape, so it maps almost one to one: 

event["~standard"] = {
  vendor: "h3",
  req: event.req,
  res: event.res,
  waitUntil: event.waitUntil,
};

Other frameworks can bridge their own APIs with getters and setters. Here is Hono: 

c["~standard"] = {
  vendor: "hono",
  req: c.req.raw,
  res: {
    get body() { return c.res.body; },
    set body(b) { c.body(b); },
    get status() { return c.res.status; },
    set status(s) { c.status(s); },
    headers: c.res.headers,
  },
};
App developer

Use it in any framework

import { logger, addVendorHeader } from "some-standard-library";

app.use(logger, addVendorHeader);
